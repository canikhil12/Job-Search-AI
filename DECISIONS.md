# Design Decisions

Format: `decision — why — interview talking point`

- Java records for all DTOs (no Lombok) — records give immutable, boilerplate-free data carriers built into the language — talking point: records replace Lombok's `@Value` for DTOs with zero dependencies and a smaller attack/maintenance surface; Lombok's annotation processing can fight newer JDKs.
- UUID primary keys generated in the app (`UUID.randomUUID()`) with `gen_random_uuid()` as the DB-side default — app-side generation keeps the id available before the row is flushed and avoids a DB round-trip, while the SQL default protects direct inserts — talking point: know the tradeoff vs auto-increment (no sequence contention, opaque ids, but 16 bytes and non-monotonic index inserts).
- `gen_random_uuid()` instead of the `pgcrypto` extension — it is built into PostgreSQL 13+ — talking point: one less extension to provision; `pgcrypto` is only needed on older Postgres.
- `pgvector` extension enabled in V1 despite being unused in Phase 1 — the production DB (Neon) will store embeddings for semantic matching, and enabling it up front keeps migrations forward-only — talking point: Flyway migrations are immutable once applied, so provisioning the extension early avoids a schema-drift headache later.
- Stateless JWT with access token only (no refresh token yet) — simplest thing that works for a portfolio API; refresh rotation is a later phase — talking point: be ready to explain access/refresh split and rotation.
- Fail-fast on missing/short `JWT_SECRET` (< 32 bytes) at `JwtService` construction — HS256 needs a 256-bit key or JJWT throws `WeakKeyException`; failing at startup beats failing on the first login — talking point: fail-fast config validation surfaces misconfiguration in deploy, not in production traffic.
- `ddl-auto: validate` with Flyway owning the schema — the DB schema has a single source of truth (SQL migrations), and Hibernate only checks the entity mapping matches — talking point: never let Hibernate `update`/`create` a production schema; migrations are auditable and reversible-by-forward-migration.
- Custom `AuthenticationEntryPoint` returns the same `ApiError` JSON shape as `GlobalExceptionHandler` — clients get one consistent error contract whether the failure is auth or application-level — talking point: consistent error envelopes simplify frontend error handling.
- JWT stored in localStorage (+ in-memory) — simplest approach for a stateless API portfolio project — talking point: XSS can read localStorage, so production hardening would use an httpOnly SameSite cookie with CSRF protection, or short-lived access tokens with refresh rotation; be ready to compare the tradeoffs.
- CORS config AND Vite dev proxy both present — the proxy makes local dev same-origin (browser never sends a cross-origin request), so CORS only matters in production where Vercel (frontend) calls Render (backend) cross-origin — talking point: know which mechanism is active in which environment and why removing either breaks exactly one of them.
- Supabase (managed Postgres + pgvector) instead of Neon for the production DB — same pgvector capability the plan needs, with a dashboard, connection pooler, and generous free tier already set up — talking point: both are serverless Postgres; the pgvector plan is unchanged, only the provider differs.
- Connect to Supabase via the SESSION pooler (Supavisor, port 5432), not the direct connection or the transaction pooler — the direct endpoint is IPv6-only (unreachable from IPv4 hosts like Render), and the transaction pooler (6543) drops prepared statements + advisory locks that Flyway/Hibernate rely on — talking point: know the three Supabase connection modes and which workloads each suits.
- Backend on Render (Docker), not on Vercel/Supabase — Vercel hosts frontend/serverless-JS and Supabase's functions are Deno, so neither can run a JVM; a long-lived Spring Boot service needs a container host — talking point: match the runtime to the platform; a stateless container on Render is the right home for the API.
- Frontend API base URL is an env var (`VITE_API_BASE_URL`), empty in dev and the Render URL in prod — one build artifact works in both environments, and prod deliberately goes cross-origin to exercise CORS — talking point: 12-factor config; the same bundle is promoted from dev to prod by changing config, not code.
- Embeddings via a provider-agnostic `EmbeddingClient` port — OpenAI adapter in prod, a deterministic `FakeEmbeddingClient` for tests/local — the whole ingest/match pipeline runs and is tested without an API key or network, and providers can be swapped without touching business logic — talking point: same ports-and-adapters pattern as the resume storage; testability and cost control fall out of it.
- OpenAI `text-embedding-3-small` (1536 dims) — cheap, strong retrieval quality, trivial REST; the schema's `vector(1536)` is pinned to it — talking point: embedding dimension is a schema-level commitment; changing models later means a migration + re-embedding.
- The "openai" embedding adapter targets any OpenAI-*compatible* endpoint via a configurable `EMBEDDING_BASE_URL`/`EMBEDDING_MODEL`, so OpenRouter (`openai/text-embedding-3-small`, same 1536 dims) drops in with no code change — talking point: coding to a de-facto protocol (OpenAI's) rather than a single vendor buys provider portability for free.
- Job embeddings written/queried via `JdbcTemplate`, not Hibernate — Hibernate has no native pgvector type, so the `embedding` column is unmapped on the entity and vectors go through native SQL casting to `vector`, while plain metadata reads stay on JPA — talking point: use the right tool per column; don't fight the ORM over a type it doesn't model.
- HNSW index (`vector_cosine_ops`) over IVFFlat — no training step, builds on an empty table, better recall/latency tradeoff for a small-to-medium set — talking point: know the two pgvector index types and when each fits.
- Jobs seeded from real Indeed postings on first startup (through the live embedding provider), not baked-in vectors — embeddings are provider-specific, so seeding through the pipeline keeps them consistent with whatever model is active; the deployed backend can't reach the session-only Indeed MCP at runtime, so the data is bundled — talking point: separate build-time data sourcing from runtime dependencies.
- Flyway `baseline-on-migrate: true` with `baseline-version: 0` — Supabase's `public` schema already holds the pgvector extension's objects, so Flyway's first run tripped its "non-empty schema, no history table" guard; baselining at 0 (not the default 1) initializes the history table while still applying V1 — talking point: know why Flyway guards non-empty schemas, and why the baseline version must sit below your first real migration or that migration is silently skipped.
- `server.port` binds `$PORT` — PaaS hosts (Render) inject the port to listen on; hardcoding 8080 would fail their health check — talking point: apps must adapt to the platform-assigned port.
